* Honest interpretation

*The C-axis question is ANSWERED, and the answer is tier-dependent* --
this run's headline finding:

- *At the strong tier, verification clearly helps.* Mean score rose
  from 0.504 to 0.605 (6q) / 0.547 to 0.726 (5q, excluding the errored
  q6) -- a delta of +0.10 to +0.18 depending on how the one error is
  counted. Per-question, the gains are concentrated exactly where
  single-strong was NOT already saturated: q2 (+0.25, 3/8->5/8), q3
  (+0.5, 4/8->8/8, perfect), q5 (+0.14, 3/7->4/7). Where single-strong
  was already high (q1, q4), verify-strong ties rather than improves
  -- consistent with a real saturation ceiling, not a broken
  mechanism. Trap adoption at the strong tier stayed at effectively
  zero either way (the one apparent hit is a scorer false positive,
  see above). q3 in particular is a strong existence proof: an
  under-specified strong single-shot answer (4/8, missing several
  required legs) became a fully-correct KB-grounded synthesis (8/8)
  purely from the verify machinery, with zero contested claims even
  needed -- the 3-member self-consistency + judge synthesis alone
  filled the gaps that a single sonnet call missed.
- *At the weak tier, verification does NOT help in this run,* and may
  be net-negative. Mean score fell slightly (0.402->0.369, or
  0.426->0.414 excluding q6), and trap-adoption did not improve
  (tied 3=3 by sum, and verify-weak introduced a NEW double-trap
  failure on q1 that plain single-weak did not have). The one clean
  REFUTED-claim gate hit in the whole battery *did* happen at the weak
  tier (q3, 750V), so the KB-grep/skeptic mechanism itself is not
  broken at haiku tier -- but a haiku *judge* still appears unreliable
  enough at *synthesizing* the verdict-annotated candidates that the
  net effect on final-answer quality is a wash or slightly negative.
  This matches the Doc 61 code comments' own caution about haiku
  extraction/synthesis fidelity being an open question, and matches
  the "sovereign panel discarded a correct answer for a hallucinated
  one" precedent cited in =anvil-fusion-verify.el='s commentary.
- Neither tier fully saturated across all 6 questions (unlike 8e/
  8e-hard, which is the whole point of this battery), so this run does
  distinguish the two tiers meaningfully rather than reporting "no
  signal because everything already maxes out."

* Deviations from the spec

- Arm 3 (verify-weak) was NOT dropped -- a harness-only =haiku-pair=
  panel (2 haiku members + haiku judge) was registered at runtime via
  =(push ... anvil-fusion-panels)= inside =ask-one.el=, no module file
  touched, matching the spec's "simplest robust path."
- =anvil-fusion-ask='s own default =:max-rounds 1= was left as-is for
  every verify-arm call (no override) -- a critique round could and
  did fire (observed q1, q2 candidate disagreement); this was a real
  cost/time driver (verify-strong runs took 14-17 min / ~$2-4 each vs.
  ~1-2 min / <$0.05-0.5 for the single/weak arms) but was left alone
  rather than capped, since capping it would have changed the exact
  mechanism the spec asked to measure.
- One retry was spent on q6 verify-strong (spec only mandates a retry
  during the SMOKE phase for structural errors; this was a normal
  battery item that simply ran long twice). Given q1-q5 verify-strong
  all completed cleanly on the identical code path, this reads as
  question-specific variance, not a harness bug, and a second retry
  was not attempted (time/budget discipline).
- The initial q1 verify-strong smoke attempt was run in the foreground
  under my own tool's ~10-min call ceiling and had to be killed and
  relaunched via background+poll once the true wall time (938s/~15.6
  min) became apparent -- a harness/tooling fix on my side, not a
  module fix, and not a second "structural error" retry against the
  fusion machinery itself (the module never errored).
- KB roots were set once for the whole process via =(setq
  anvil-fusion-verify-kb-roots ...)= rather than a per-call =let=,
  functionally identical for this single-ask-per-process design (no
  concurrent callers to isolate from).

* Limitations

- Single run per (question, arm) -- no repeated sampling, so the
  deltas above are point estimates, not statistically tested.
  Especially the strong-tier deltas (driven heavily by q3's 4/8->8/8
  swing) could look different on a second seed.
- 6 questions is a small battery; q6's verify-strong error further
  thins the strong-tier N to 5 for that arm.
- =score.sh= is a plain regexp/substring scorer with no context
  awareness -- it cannot distinguish "adopted a trap value as the
  answer" from "mentioned and explicitly rejected a trap value for
  completeness" (demonstrated concretely on q1 verify-strong above).
  The trap-adoption counts in this report should be read with that
  caveat; a qualitative read of the actual answer text is included
  wherever a trap was scored so the reader can judge for themselves.
- Cost for the two failed q6 verify-strong attempts is NOT included in
  the $22.20 recorded total below -- each attempt's in-memory
  cost-capture list died with the hard-killed process, so real spend
  is somewhat higher than the recorded figure (unquantifiable from
  this side; likely a few dollars given partial member/skeptic
  sub-task completion before each kill).
- Both single/weak arms had full default Claude Code tool access in
  their nested calls (no =:allowed-tools= restriction was applied) --
  observed side effect: some panel members chose to Write their answer
  into a file named after the question's org =#+title= inside the
  scratch cwd, in addition to returning it as their response text.
  Harmless (contained to a throwaway scratch dir, cleaned up after the
  run, never read by the scoring harness) but worth noting: a "plain"
  arm in this design is not guaranteed to be zero-tool-use, only
  zero-verify-machinery.
