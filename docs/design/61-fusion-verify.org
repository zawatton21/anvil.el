* 0. Executive summary

Doc 54 (fusion harness) and Doc 55 (longrun) shipped a working fan-out -> judge
ensemble, but the 2026-06-15/16 evals recorded three hard findings:

1. *Fusion never beat a strong single model in any tested condition*
   (=eval/results-hard-2026-06-15.org=): cloud members saturate the benchmark,
   local members collectively lack the knowledge the judge would need.
2. *The judge can discard a correct candidate in favor of a hallucinated one*
   (=eval/results-panel-compare-2026-06-16.org=: sovereign panel answered
   100 MOhm where a member had the correct 0.1 MOhm). The judge selects on
   plausibility of prose, not on verified truth.
3. Weak-provider distillation loses tails mechanically
   (=results-longrun-weakdistill-2026-06-16.org=).

This doc addresses the goal behind Doc 54 — *reproduce Fable-5-class capability
on Opus 4.8* — by shifting the design center from "synthesize better prose" to
"*verify before synthesizing*". The Fable 5 / Opus 4.8 gap observed in practice
is less about one-shot knowledge and more about long-horizon planning,
verification, and self-correction accuracy. Three phases (numbering continues
Doc 54's 1-5):

- *Phase 6 — Verifier-grounded judge*: extract contested claims, check them
  against evidence (local KB tools, execution for code), feed verdicts to the
  judge. Directly kills failure mode (2).
- *Phase 7 — Opus self-consistency panel (=opus-solo=)*: claude x k members
  diversified by role-lens + temperature, judged by the Phase 6 verifier judge.
  No codex/gemini wiring dependency (both broke during the 06-15 evals).
- *Phase 8 — Agentic fusion (deep x wide)*: plan-level fusion + "longrun step =
  fusion panel" (deferred in Doc 55 as Phase 4+), with a verify gate between
  steps to stop error propagation.

Plus a debt bundle (Phase 6d'): async-path critique loop, eval egress
inference, and an unsaturated eval battery.

* 2. Phase 6 — Verifier-grounded judge

Layered on the orchestrator public API only (same discipline as Doc 54).
New module =anvil-fusion-verify.el=.

** 6a. Claim extraction (divergence mining)
- After =consensus-collect=, run a cheap extraction pass (judge provider,
  =haiku=-tier acceptable) that lists *contested claims*: factual assertions on
  which candidates disagree or that only one candidate makes.
- Output: list of plists =(:claim STR :candidates (NAME...) :kind fact|number|code|citation)=.
- Cap: =anvil-fusion-verify-max-claims= (default 5) — verify only the claims
  that would change the final answer.

** 6b. Evidence check per claim
Per-claim verification strategies, dispatched by =:kind= and panel egress:
- =citation= / =fact= (domain): query local KB — =notes-lexical-search=
  (tools/semantic-search lexical mode), hourei org DB under =node/=. Local
  tools are egress-safe, so *sovereign panels get verification too*.
- =number=: KB lookup first; if the panel is =external=, optionally one web
  check (=anvil-http=). Never for =local-only= panels.
- Adversarial refutation vote: fan the claim to N skeptics
  ("try to refute; default to refuted when uncertain") via
  =orchestrator-consensus-submit=; majority-refuted claims are marked FALSE.
  N = =anvil-fusion-verify-skeptics= (default 2; 3 for =rigorous=).
- Verdicts: =CONFIRMED= / =REFUTED= / =UNVERIFIED= with a one-line evidence
  pointer (file:line or refutation summary).

** 6c. Execution-based verification (code tasks)
Port of the nelisp-llm agent-harness principle (execution reward > text
judging):
- When the task is code (=:task-kind 'code= or heuristic detection), run each
  candidate patch in an isolated worktree (=anvil-git= worktree helpers, same
  plumbing as orchestrator =:worktree=) and gate on build / ERT / user-supplied
  check command (=:check-cmd=).
- A candidate that fails execution is excluded from synthesis regardless of
  prose quality. Judge receives pass/fail per candidate.

** 6d. Verdict-annotated synthesis
- Extend the Doc 54 structured judge template: the judge prompt now includes
  the claim table with verdicts and *must not adopt a REFUTED claim*; when all
  candidates carry a REFUTED load-bearing claim, the judge must say so rather
  than synthesize confidently.
- This is a prompt-template + data-plumbing change in =anvil-fusion.el=;
  the old template remains as fallback (=anvil-fusion-judge-template= untouched,
  new =anvil-fusion-verify-judge-template=).

** 6d'. Debt bundle (small, shipped with Phase 6)
- Critique loop in the async/MCP path (Doc 54 §12c — async is still
  single-round).
- =anvil-fusion-eval= egress inference from provider (ollama currently
  hard-coded =external=, Doc 54 §12b).
- =fusion-ask= MCP tool grows =:verify= flag (default on for =quality= /
  =claude-pair=; on-with-local-tools-only for =sovereign=).

** 6e. Unsaturated eval battery
- New =eval/cases-agentic.el= + harder domain cases where single Opus is
  measurably below ceiling (target: single-model score 0.4-0.7 band, so uplift
  is observable). Re-run panel-compare; acceptance = the 0.1 MOhm class of
  failure no longer occurs (verified judge refuses the hallucinated number).

* 3. Phase 7 — Opus self-consistency panel (=opus-solo=)

- New panel in =anvil-fusion-panels=:
  =(opus-solo . ((members . ((claude . "claude-opus-4-8") x3)) (judge . (claude . "claude-opus-4-8")) (egress . external)))=
  with per-member diversity injected by:
  - role-lens (existing =anvil-fusion-lens=: correctness / completeness /
    domain / skeptic), and
  - sampling diversity where the provider CLI allows it (temperature /
    "consider an unconventional approach" lens as fallback).
- Rationale: evals showed cross-vendor diversity is fragile operationally
  (auth, wiring) and unnecessary when the base model is strong; claude-pair
  was the most robust panel. =opus-solo= is claude-pair generalized to k
  members + verifier judge — the most direct answer to "Fable 5 performance on
  Opus 4.8 only".
- Cost note: k=3 + judge ~= 4x single ask; router/preset should keep this for
  hard/important prompts (existing =anvil-orchestrator-presets= mechanism).

* 4. Phase 8 — Agentic fusion (deep x wide)

Where the real Fable-gap lives: multi-step tasks.

** 8a. Plan fusion
- =anvil-fusion-plan=: fan out *plans* (not answers) for a task, judge merges
  into one plan (verifier judge checks plan claims against repo/KB reality:
  files exist, APIs exist).

** 8b. Longrun step = fusion panel
- Implement the Doc 55 deferred composite: a longrun quest step may execute as
  a fusion ask (=:step-panel= option). Bounded by budget guards (Doc 47) —
  panel steps only where the step is marked =:hard=, single provider otherwise.

** 8c. Verify gate between steps
- After each step, run the Phase 6 verifier on the step's digest before it
  enters the state (stops error propagation into subsequent steps — the
  distill-tail-loss analog for correctness). Failed gate -> step retried once
  with the refutation as feedback, then surfaced.

* 5. Phase 9 (sketch, not committed) — Verified-trajectory library

STaR / expert-iteration without weight updates (nelisp-llm pattern, API-model
version): store (question, plan, verified answer, verdict evidence) tuples that
*passed the Phase 6 gate* into a SQLite store (anvil-memory or its own table);
retrieve top-k similar exemplars (FTS5) and prepend to future panel prompts.
Quality control is inherent: only verified wins enter. Design in detail after
Phase 6-7 produce trajectories worth keeping.

** 8f. Agentic members + execution-permission passthrough (design)

8e's operational finding and the "agentic member" gap are the same root
defect: `anvil-fusion-panel-tasks` builds member task plists carrying only
:provider :prompt :name [:model] [:cwd], while the orchestrator already
honors per-task :permission-mode (claude path) and :sandbox (codex path) —
members simply never receive them, so a panel member (or a longrun coding
step's claude child under the default acceptEdits) cannot run its own
build/tests or consult tools.

Design:
- `anvil-fusion-panel-tasks` gains an optional MEMBER-EXTRAS plist merged
  into every member task (whitelist: :permission-mode :allowed-tools
  :sandbox :no-worktree :timeout-sec). Providers ignore keys they do not
  read, so one merged plist serves all member providers safely.
- `anvil-fusion-ask` gains :member-extras (passthrough) and :agentic
  (convenience: a safe preset — claude members get :permission-mode
  "bypassPermissions" ONLY when a scratch :cwd outside any user repo is
  supplied, else :allowed-tools grant for the build command; codex members
  get :sandbox "workspace-write"). Member prompts under :agentic get an
  appended instruction block: you may run commands/tools in CWD to check
  your answer before finalizing it.
- `anvil-fusion-longrun-run` / async / plan: passthrough of :member-extras
  to their panel calls; longrun's own single-provider step task accepts
  the same extras (this is the 8e permission-knob follow-up, closed here).
- Sovereignty: local-only panels reject extras that would grant network
  egress tools; local execution remains allowed.
- Safety: :agentic defaults nil everywhere; docstrings must spell out the
  bypassPermissions blast radius and the scratch-cwd requirement.

** 10. Multi-round debate (design)

Today's critique loop is a single divergence-triggered re-round. Deepen it
into a bounded debate: when candidates diverge after round 1, each member
receives the OTHER candidates' answers (deduped per Doc 62 Phase 7
rendering) plus the verified-claims table, and must either defend or
revise; re-judge after each round. Termination: convergence
(should-loop-p), max-rounds (existing defcustom now meaning debate depth),
or a judge-declared resolution. Verify runs once on round 1 claims plus
incrementally on NEW claims surfacing in later rounds (extraction diff by
claim-key hash — reuses the Phase 4 cache so re-verification is cheap).
Cost note: each debate round ~ one member fan-out + judge; router should
only enable depth > 1 at the HIGH tier.

** 11. Router auto-calibration (design)

The Doc 62 Phase 2 router logs every decision (risk, reason, tier). Close
the loop offline: a calibration command reads the log joined with
follow-up outcome signals — verify verdicts of the escalated runs (were
HIGH escalations justified: did claims get refuted?), user re-ask within
the session (proxy for a wrong LOW), cost per decision — and proposes (not
auto-applies) threshold/mapping changes as a diff to
`anvil-fusion-route-escalation` with the supporting counts. Manual apply
keeps the human in the calibration loop until enough log volume exists.

8e-hard measured 2026-07-05 (benchmarks/doc61-phase8e-hard/,
results-8ehard-2026-07-05.org, ~$4.81, 6 runs). The de-saturation attempt
FAILED to de-saturate: on the one-shot-resistant battery (naive
visible-passing patches provably fail the hidden tests) baseline was still
3/3 == full 3/3 hidden completions, every run finished in 1 step (mean
baseline 1.33 / full 1.00), panels never fired (hard-only skips step 1 and
every quest ended at step 1) and all 3 gates passed first try. The C-axis
(does panel+verify raise completion over a plain baseline?) is STILL
unproven — not because the harness is wrong but because a single Claude
Code step-agent WITH real Bash/build execution already self-corrects to
ceiling on coding tasks: it runs the code, sees the failure, and fixes it,
so the difficulty levers that would trip a text-only one-shot model
(hidden invariants, multi-file cascades) do not trip an executing agent.
Honest conclusion after two saturated runs: for CODE tasks where the agent
can execute and iterate, the ensemble/verify machinery has little room to
add completion — the execution oracle is doing the verification already
(this is 6c's premise from the other direction). The harness's measurable
value must be sought where there is NO cheap execution oracle: fact/
citation-critical Q&A (6e's 0/10 hallucination-adoption win), KB-grounded
domain answers, and multi-hour tasks exceeding a single agent's context —
none of which these coding fixtures exercise. A fair C-axis test needs a
NON-code long-horizon task with a checkable-but-not-self-evident answer.
NEW design gap found: anvil-fusion-longrun--default-distill-fn passes no
member-extras, so the distill (and any future verify) phase always runs
under the orchestrator default permission mode — harmless today (the step
phase already ran the build) but a real wall if distill/verify is ever
given execution duties. Follow-up: thread member-extras into the distill
fn.

8g measured 2026-07-05 (benchmarks/doc61-phase8g/, results-8g-2026-07-05.org,
$22.20, 6 KB-verifiable domain questions x 4 arms). FIRST non-saturated,
positive C-axis signal in the campaign — these questions have no cheap
execution oracle, so a wrong intermediate is caught only by KB grounding.
Mean rubric score (score/max): single-weak 0.40, single-strong 0.50,
verify-weak 0.37, verify-strong 0.60. Deltas: verify-strong minus
single-strong = +0.10 (+0.18 excluding q6's errored run) — real uplift
concentrated where the plain sonnet answer had headroom (q3 4/8 -> 8/8);
verify-weak minus single-weak = -0.03 (NO help at the haiku tier; haiku
judge/synthesis too unreliable, though the KB-refutation mechanism itself
fired correctly once). Mechanism demonstrated, not asserted: on q3
verify-weak a haiku member claimed "測定電圧は直流750V"; the skeptic vote
REFUTED it against node/20260614220903_catchall_box.org:2349 (JIS C 1302
rated voltages 25/50/100/125/250/500/1000V, no 750V) and the synthesis
adopted 500V. Trap adoption: single-strong 0/6, verify-strong ~0 — at the
strong tier the uplift is added completeness, not trap avoidance (sonnet
already dodges traps). Honest bounds: single run, 6 questions, rubric-grep,
one scorer false-positive ("25Ω" is a rejected in-text alternative), and q6
verify-strong hard-killed twice by the 20-min cap with zero completions
(panel + verify + critique can exceed 20 min on a hard question — follow-up:
bound verify-strong wall/cost).

Campaign conclusion (8e / 8e-hard / 8g): the fusion verify harness adds
measurable capability specifically where there is NO cheap verification
oracle and the base model is strong-but-not-saturated — grounded domain
Q&A (+0.10-0.18 here; 6e's 0/10 hallucination adoption). It saturates on
coding (execution self-corrects — 8e/8e-hard) and does not lift a weak
(haiku) model. So "raise Opus/Sonnet toward Fable" is TRUE but scoped:
modestly and measurably on fact/citation/KB-grounded work; not on tasks a
strong model with tools already nails, and not by rescuing a weak model.

Recommended order: 6 -> 7 -> 8 (Phase 6 fixes a recorded, harmful failure mode
and is measurable immediately; Phase 7 is a small addition on top; Phase 8 is
the heavyweight design).

  synthetic cases / 14 gold claims (=benchmarks/doc61-phase6a/=, 16 live

  general questions the skeptic vote is the only verifier — is N=2 enough?
- 8b cost envelope: panel-per-step multiplies longrun cost; define the =:hard=
  step marking heuristic (divergent digest? prior step retried?).
- [RESOLVED 2026-07-03] Phase 7 sampling diversity: the claude CLI exposes no
